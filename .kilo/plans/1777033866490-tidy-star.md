# Evaluating Config Format for Premflow

## Overview
The current config system uses a simple key=value text file format. The user finds the parsing "messy" and is asking about native C support for YAML/JSON formats. This plan evaluates alternatives and proposes a path forward for cleaner config parsing while maintaining premflow's lightweight nature.

## Current State
- **Format**: Simple key=value pairs in ~/.premflow/config.txt
- **Parsing**: Manual string splitting, trimming, and comparison in C
- **Pros**: No dependencies, simple, fast
- **Cons**: "Messy" parsing code, limited structure, no validation

## C Language Support Analysis

### Native Support
- **JSON**: No native support in standard C
- **YAML**: No native support in standard C
- Both require external libraries for parsing/serialization

### Library Options

#### JSON Libraries
- **cJSON**: Lightweight (2-3KB), single header file, MIT license
- **json-c**: More feature-rich but larger
- **yyjson**: High performance, but newer and less tested

#### YAML Libraries
- **libyaml**: Reference implementation, but heavy (~200KB)
- **yaml-cpp**: C++ only, not suitable for C
- **libcyaml**: C library, schema validation, but complex

### Feasibility Assessment
- JSON is more suitable for C: smaller libraries, simpler parsing
- YAML is overkill for this use case (nested structures not needed)
- Adding any library increases binary size and introduces dependencies
- Premflow's "one tiny C binary" philosophy favors minimalism

## Proposed Solution
Switch to JSON format for config if the parsing messiness is a significant issue. Use cJSON as it's the most lightweight and C-compatible option.

## Implementation Plan

### 1. Evaluate Impact
- Measure current parsing code complexity
- Assess user pain points with current format
- Consider if JSON benefits outweigh the dependency

### 2. Library Selection
- Choose cJSON for minimal footprint
- Add as git submodule or vendor the header

### 3. Config Format Design
- Convert current key=value to JSON object:
```json
{
  "player": "paplay",
  "pomo_complete": "paplay /usr/share/sounds/freedesktop/stereo/complete.oga >/dev/null 2>&1",
  "pomo_start": "paplay /usr/share/sounds/freedesktop/stereo/phone-incoming-call.oga >/dev/null 2>&1",
  "task_complete": "paplay /usr/share/sounds/freedesktop/stereo/bell.oga >/dev/null 2>&1"
}
```

### 4. Code Changes
- Replace read_config() with JSON parsing
- Update create_config_template() for JSON format
- Maintain backward compatibility (auto-convert old format if present)

### 5. Testing
- Verify JSON parsing works
- Test error handling for malformed JSON
- Ensure binary size increase is minimal
- Test on target platforms

### 6. Documentation
- Update comments in config file
- Document new JSON format in help text

## Tradeoffs
- **Pros**: Cleaner parsing code, better error handling, potential for future config extensions
- **Cons**: Adds dependency (~2KB), slight binary size increase, complexity for users unfamiliar with JSON
- **Risk**: If cJSON has issues, alternatives exist but may be larger

## Recommendation
Stick with current txt format unless parsing messiness is blocking development. The simplicity aligns with premflow's philosophy. If proceeding with JSON, cJSON is the best choice for C applications.
